# SakuraScholar 技术可行性说明

> 版本：v1.0 · 2026-08-24 · 随参赛作品"其他辅助材料"提交

## 1. 技术路线成熟度

本项目采用成熟、低门槛的技术栈，全部为公开可用的稳定组件：

| 层次 | 选型 | 成熟度说明 |
| --- | --- | --- |
| 服务框架 | Python 3.10+ / FastAPI / Uvicorn | 业界主流 Web 框架，异步支持良好 |
| 前端 | 原生 HTML/CSS/JS（单页） | 零构建依赖，任何静态服务器可托管 |
| 检索通道 | arXiv / OpenAlex / CrossRef / Semantic Scholar | 四大公开学术 API，均无需付费 Key 即可使用（OpenAlex 支持 mailto 免计费） |
| 本地语义 | PaSa 官方公开论文标题库 + FastEmbed BGE-small | 数据公开可下载，向量化本地完成 |
| LLM | Mock / OpenAI 兼容 / DeepSeek / 千问 / GLM / Ollama 本地模型 | 统一抽象层，可自由切换；鼓励开源模型 |
| 评测 | PaSa / AstaBench 官方测试集（本地化） | 数据已下载入库，评分口径与官方一致 |

## 2. 数据来源与合规性

- 评测数据来自 PaSa（bytedance/pasa，AutoScholarQuery 1000 条、RealScholarQuery 50 条）与 AstaBench（allenai/asta-bench，paper_finder_bench 267 条、LitQA2 199 条），均为官方公开发布，已本地化存储；
- 本地语义语料使用 PaSa 官方公开的 paper_database 论文标题库（约 20 万篇），仅用于检索召回，不读取评测答案；
- 项目在大赛期间独立开发，借鉴的开源工作均在 README / 项目文档中严格标注引用；
- 运行时数据（收藏夹、账号、配置）本地存储，不对外泄露，不提交到仓库。

## 3. 可复现性

- **无 Key 可跑通**：使用 Mock LLM + 本地语料即可完整运行检索与 Web 演示；
- **评测可复现**：`python3 run_eval.py --n 50 --benchmarks real_scholar --real --llm deepseek --output /绝对路径/结果.json`，评分口径（arXiv/DOI/S2 corpusId 三 ID 归一化精确匹配）固定，结果归档 JSON；
- **数据本地化**：所有官方测试集无需联网下载，离线可评测（受外部 API 额度影响的通道会自动降级并注明）。

## 4. 质量与测试

- 单元测试 32 例全绿（`pytest tests/ -q`），覆盖引擎、评分、结构化输出、接口关键路径；
- 真机 UI 冒烟测试脚本 `src/tests/ui_smoke.js`（Playwright）可一键验证页面可达性与核心交互；
- 检索后端统一 `_safe_call` + 熔断器模式，外部 API 失败自动降级，不拖垮流水线；
- 前端不依赖浏览器 API 做关键逻辑，模板改动经 `node --check` 校验。

## 5. 部署与资源需求

| 模式 | 资源需求 | 说明 |
| --- | --- | --- |
| 最低（Mock） | 普通 PC，无需 GPU | 离线演示、功能验证 |
| 推荐（本地 Qwen） | 8GB+ 内存或消费级 GPU | Ollama 拉起 Qwen2.5-7B 等模型 |
| 增强（DeepSeek） | 普通 PC + API Key | 效果最好的在线判分，成本约 24 次 LLM 调用/查询 |

## 6. 成本估算

- 本地模式：推理免费（仅耗电），评测 50 条约 3 小时；
- DeepSeek 模式：单查询约 24 次 LLM 调用，按 DeepSeek 公开价格估算单查询成本远低于 1 元；
- OpenAlex / S2 匿名额度每日重置，系统自动限流退避，不会产生意外账单；
- 预算分级机制（按轮次/通道分配调用次数 + deadline 逐批截断）从机制上控制成本。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| S2 匿名额度 429 | 语义通道与 corpusId 映射缺失 | 串行限流 + 熔断 + OpenAlex/本地语料接管 |
| OpenAlex 匿名额度耗尽 | 候选池变小 | mailto 免计费通道 + 双向引文补偿 |
| 当前 F1 低于公开参考线 | 与 SOTA 有差距 | 补全本地索引、恢复 S2、全量评测后继续迭代（详见项目文档 7.8） |
| 全量评测耗时长 | 结果不完整 | 守护进程运行 + 结果增量归档 |

## 8. 结论

本项目的技术路线、数据来源、评测方法与工程实现均公开可查、可复现、可部署，满足赛题对"方案具备合理的成本控制意识、鼓励开源模型、对接真实学术 API"的全部技术要求，具备真实的工程落地条件。
