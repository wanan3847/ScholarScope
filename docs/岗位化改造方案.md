## 二、定位话术（简历/面试口径）

**一句话**：一个从零实现的多 Agent 学术检索系统：查询规划 → 5 通道并行召回 →
BGE 语义预筛 → LLM 批量判分 → RefChain 双向引文扩展 → 反馈闭环，并配套
MCP 工具化、LLM-as-a-Judge 评测与分布式后端改造。

**差异化叙事**：不套 LangChain，核心链路自研（规划/判分/扩展/排序可逐行讲清），
再补"框架对照 demo"证明工程迁移能力 → 这正是面试官最想听的"原理 + 落地"组合。

## 三、AutoDev 概念借鉴（只借概念，不做软件工程 Agent）

AutoDev 是"软件工程任务执行平台"，本方案**不换领域**，但以下 7 个设计点对学术 Agent
同样成立且多数已有底子——借的是抽象方式与评测方法，不是业务场景。

| AutoDev 能力 | 学术 Agent 可借鉴点 | 现有底子 | 改造动作 |
| --- | --- | --- | --- |
| Planner–Task DAG–Scheduler–Executor–Reviewer 闭环 | 复杂查询拆成子任务 DAG：5 通道检索无依赖 → 并行；RefChain 扩展依赖首轮结果 → 拓扑执行 | QueryPlanner 已拆子查询；`data/schemas.py` 已有 `QueryGraph`/`GraphRelation`；检索已 ThreadPool 并行 | 把 SPAR2 执行流程显式建模为 Task DAG + Scheduler（P1 核心） |
| Tool Calling 可扩展 Agent Loop + 异常检测/自动重试/失败重规划 | 检索通道抽象成统一 Tool 注册表（arxiv / openalex / crossref / s2 / local / refchain），统一异常检测与降级，为 MCP 提供统一出口 | 5 个检索后端 + tenacity 重试 + 熔断（`_safe_call` 模式） | `Tool` 抽象 + 注册表；通道失败时生成补充查询重规划（P1） |
| DAG 并行调度降低整体延迟 | 子查询并行 + 依赖拓扑执行 → 直接压 P50（当前真实模式 170s+，是最大体验痛点） | ThreadPoolExecutor 并行骨架已存在 | `DAGScheduler`（asyncio 拓扑排序 + 并发池，无外部依赖）（P1） |
| 长期 Memory + RAG 跨任务上下文复用 | 用户反馈/收藏/已阅 → 向量记忆库 → 个性化重排（个人学术偏好），跨会话复用 | `collections.py` + `feedback_loop.py` + BGE 数据全齐，缺"记忆写入 + 检索注入"环节 | Memory 模块：写记忆 → 检索时召回注入（P2） |
| Reviewer / Reflection 验证 + 失败重规划 | 判分后 LLM 自检"候选是否覆盖查询意图"，不足则生成补充查询再检索 | 迭代检索 BFS + 文档驱动查询生成（本质就是 reflection，只是未命名、未量化收益） | 显式 `Reviewer` 环节 + 评测里量化 reflection 前后指标（P1） |
| 四策略对比实验（成功率/耗时/Token） | Single-Agent vs Reflection vs Multi-Agent vs DAG 并行，用 F1@10 / Recall@20 / 延时 / Token 量化 | `run_eval.py` + 4 个官方 benchmark + 既有 ablation 机制 | 评测扩展四策略模式 + 对比报告（P1-P2，面试杀手锏） |
| Docker 一键部署 | 学术检索服务容器化，评委/面试官一条命令起服务 | 无 | Dockerfile + docker-compose（P2） |
| Shell / Git / 代码检索工具 | **不借鉴**（学术场景用不到，避免过度设计） | — | — |
| LangChain 作为核心 | **不引入**，理由见第四节 | — | — |

**一句话总结**：AutoDev 最值得借的两样东西是「把执行流程当 DAG 调度」和「把不同 Agent
架构做成可量化对比实验」——前者解决你当前 P50 170s 的真痛点，后者是面试里最能打的亮点。

## 四、技术选型：为什么核心不用 LangChain / LangGraph

> 本节合并自原 `docs/技术选型_LangChain与LangGraph.md`（2026-08-30）。

### 4.1 先分清两件事（结论完全不同）

| 问题 | 结论 |
| --- | --- |
| A. 把现有核心（SPAR2：规划/检索/判分/扩展/评测）整体迁到 LangChain | **不建议**，理由见 4.2 |
| B. 新增模块（DAG 调度 / Memory / 多智能体协作）用 LangGraph 实现 | **可以**，按需选用，理由见 4.3 |

不区分这两件事，讨论就会变成"用不用框架"的一刀切；正确答案是：
**核心自研 + 框架对照 demo + 新模块可选框架**。

### 4.2 为什么不动核心（4 条硬理由）

1. **已有成绩不可比，换框架 = 自废武功**：F1@10=0.1055、P50 延时、Token 消耗全在自研
   SPAR2 上验证，沉淀在 `docs/评测记录.md`；换框架后基准全部作废，BGE 阈值 0.4、
   截止日期过滤、ID 归一化、通道降级等细节不在框架原语里，要重写胶水代码重调参，
   F1 大概率倒退，提分记录（0.0579 → 0.0833 → 0.1055）作废。
2. **面试叙事吃亏**：JD 的"熟悉 LangChain"要求**会用**即可；自研核心能逐行讲
   Planner/Judge/RefChain 原理，换框架后只会被问"你调了哪些参数"，变成调包侠叙事。
3. **框架摩擦 + 依赖膨胀**：多通道合并、RefChain、静默降级都不在框架原语里，只能
   "绕过框架"写胶水代码；LangChain 抽象层变动频繁（0.3 / 1.0 / LangGraph 分家）；
   项目现在零框架依赖、离线可跑，这是强工程亮点，不该牺牲。
4. **你已经有自己的"框架"**：`llm/router.py`、`agent/orchestrator.py`、
   `evaluation/runner.py`、`retrieval/` 本身就是框架级抽象；简历写"自研 Agent Harness"
   比"用了 LangChain"更有含金量。

### 4.3 框架能帮什么？什么时候值得用

**LangGraph 真正有用的点**：`StateGraph` 显式表达状态机与节点依赖（天然适合
Planner→检索→Judge→Reviewer）；Checkpoint / Memory 跨轮次持久化；多智能体协作模式
（Supervisor / Handoff）；Human-in-the-loop。

**建议落点（折中方案）**：
1. 核心 SPAR2 不动，保留全部评测资产；
2. 写 `examples/langgraph_demo.py` + `examples/llamaindex_demo.py` 对照 demo
   （设计见第五节），证明会用框架、能讲清框架抽象和坑；
3. 新增 DAG / Memory 模块若用 LangGraph 实现，就补一个自研 vs LangGraph 的 A/B
   （同任务集，F1/延时/Token），用数据说话，反而变成亮点。

**什么时候才值得把核心换成框架**：需要大量现成生态集成且自研成本过高；团队技术栈
强制统一；或你已用框架做过 2-3 个完整项目、能讲清底层原理时。

### 4.4 面试口径（直接背）

> "核心链路是我从零实现的：查询规划拆子任务，5 个检索通道并行召回，BGE 语义预筛，
> LLM 批量判分，RefChain 双向引文扩展，再跑官方 benchmark 量化 F1 和延时。
> 不选 LangChain 是因为多通道合并、判分、降级这些细节不在它的原语里，自研能逐行讲清原理、
> 完全可控。框架我也用过：我用 LangGraph 的 StateGraph 复刻了同一套 Planner-检索-Judge-Reviewer
> 链路做对照 demo，新增模块如果上框架我也能讲清楚它的抽象层次和适用边界。"

要点：**不贬低框架**，强调"自研可控 + 框架会用"双线叙事。

### 4.5 决策对照表

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 核心迁 LangChain | 生态丰富、JD 字面对齐 | 基准作废、调参重来、面试变调包、依赖膨胀 | ❌ |
| 核心迁 LangGraph | 状态机表达贴合 DAG/多智能体 | 同上（核心全重构风险） | ❌ |
| 核心自研 + 对照 demo | 保留全部资产 + 框架熟练度双占 | 多写两个 demo（各 1-2 天） | ✅ 推荐 |
| 核心自研 + 新模块 LangGraph + A/B | 新模块开发快、有量化对比 | 引入依赖、需锁版本 | 🟡 可选 |

### 4.6 如果坚持要改核心：低风险路径（兜底方案）

1. 分支上先写 `examples/langgraph_demo.py`，用同任务集跑 10-20 条 A/B，
   对比 F1@10 / Recall@20 / P50 / Token（复用 `run_eval.py` 指标口径）。
2. 只有 LangGraph 版在**至少两个 benchmark 上不显著落后**（±0.01 以内）才考虑迁移。
3. 迁移按模块走：检索编排 → 多智能体协作 → 评测，每步跑全量回归（32 个单测 + benchmark 对比）。
4. 保留双引擎开关（`--engine spar2|langgraph`），数据说话后再决定默认引擎。

## 五、框架对照 demo（设计文档，暂不落地代码）

### 5.1 验收标准（先定标准再做）
- 默认**离线可跑**（MockLLM + Mock 检索后端，零 API key）；`--real` 走真实 API。
- 每个 demo 单文件、可 `python examples/xxx_demo.py` 直接运行，输出即"面试素材"。
- README 里放运行截图或 30s 录屏。
- 核心链路零改动，32 个单元测试保持全绿。

### 5.2 Demo A：`examples/langgraph_demo.py`（LangGraph）

**展示点（对应 JD 高频能力）**：
- `StateGraph` 状态机：节点 + 条件边 + TypedDict 状态 Schema（Agent 编排）；
- `Send` API：子查询动态扇出，无依赖任务并行执行 ≈ DAG 并行调度；
- 条件边：Reviewer 判定候选不足 → 回 Planner 重新规划（Reflection 循环）；
- `MemorySaver`：跨轮次状态持久化（长期 Memory 能力）；
- 复用项目真实组件：`llm/router.py`（Mock/DeepSeek）+ `retrieval/` 检索后端。

**节点结构草图**：

```
START → planner ──(Send 扇出)──→ search×N（每子查询一个分支，两通道并行）
                                     ↓ 合并去重
                                  judge（LLM 批量打分 [i] score）
                                     ↓
                                  reviewer ──retry──→ planner（补子查询）
                                     ↓ done
                                    END
```

**关键实现要点**：
- planner：LLM 生成 3 个多样化子查询（复用 MockLLM 的 query 生成分支）；
- search：每分支 `asyncio.gather` 并行调 `semantic_scholar` + `arxiv` 两个后端，按 ID 去重；
- judge：拼"用户查询 + [i] 标题/摘要"批量打分 prompt，正则解析 `[i] score`；
- reviewer：高分候选 < 阈值且轮次 < 上限 → `verdict=retry`，条件边回 planner；
- 结束打印：状态轨迹（`get_state_history`）+ Top 论文 + LLM 调用次数。

**面试话术**：能同时讲清 LangGraph 的抽象（节点/边/状态/Checkpoint）和你自己
SPAR2 的实现，并说明"为什么这类框架适合表达 Agent 图，但我的领域细节仍自研"。

### 5.3 Demo B：`examples/llamaindex_demo.py`（LlamaIndex）

**展示点**：
- `Document` + `VectorStoreIndex`：本地论文库建索引（RAG 基建）；
- `Settings.embed_model`：默认 `MockEmbedding` 离线可跑，注释说明可一行换 BGE/
  SentenceTransformer/OpenAI（向量数据库能力）；
- `as_retriever(similarity_top_k=3)`：top-k 语义检索；
- `PromptTemplate` + LLM：检索结果判分/摘要（复用项目 `llm/router.py`）。

**结构草图**：`5-6 篇知名论文(标题+摘要) → 建索引 → 检索 query 的 top3 → 逐篇 LLM 判分 → 输出对比表`。

**面试话术**：能讲清 LlamaIndex 的索引结构（Node/Embedding/Retriever）与
RAG 全链路，并指出与自研检索的区别和取舍。

### 5.4 与核心的关系
- 两个 demo 是**对照示例**，不进入核心链路；核心始终是自研 SPAR2（见第四节）。
- 若想让"会用框架"更有说服力，可加第三个：用 LangChain 复刻"检索 + 判分"最小链路
  （`examples/langchain_demo.py`），三选二即可。
